FH-01 — Duplicate charge on request retry  ✓ VERIFIED

A client that retries a failed or timed-out POST /payment will trigger a second charge_card call because there is no cache lookup before the external call, so the same card is charged twice with no deduplication.

Evidence

  • inventory.json > idempotency_patterns[0]: function=process_payment, cache_checked_before_external_call=false
  • inventory.json > idempotency_patterns[0]: first_cache_read_line=null (cache is never read before the external call)
  • inventory.json > idempotency_patterns[0]: first_external_call_line=33 (charge_card called at app/payment.py:33)
  • inventory.json > idempotency_patterns[0]: first_cache_write_line=48 (cache.set written only after charge, at app/payment.py:48)
  • test_coverage_map.json: 0 of 16 tests have covers.retry=true

Captured assertion failure

FH-02 — Race condition on shared balance under concurrent requests  ✗ GAP

Two concurrent payment requests for the same user can both read the same pre-deduction balance from the unprotected _balances dict, pass the funds check, and both write back a reduced balance — effectively allowing a double-spend up to the full account balance.

Evidence

  • inventory.json > shared_mutable_state[1]: name=_balances, file=app/payment.py, has_lock_protection=false
  • inventory.json > shared_mutable_state[1]: read_lines=[20, 24] (balance read in get_balance at :20 and in charge_card at :24)
  • inventory.json > shared_mutable_state[1]: write_lines=[27] (balance decremented at app/payment.py:27)
  • inventory.json > functions[charge_card]: calls_in_order=[_balances.get, InsufficientFundsError, uuid.uuid4] — read and write are non-atomic
  • test_coverage_map.json: 0 of 16 tests have covers.concurrency=true

Captured assertion failure

AssertionError: FH-02 confirmed: both concurrent charges succeeded (2 charges).
With a correct lock only one should have been allowed.

assert 2 <= 1

Test FAILS — bug is still present.
